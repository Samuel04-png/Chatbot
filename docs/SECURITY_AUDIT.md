# Rudo security audit

> Historical discovery baseline. Local implementation is now authorized and documented in [LOCAL_IMPLEMENTATION.md](LOCAL_IMPLEMENTATION.md); original source references below describe the audited snapshot. Remote execution remains pending review.

Date: 2026-11-20. Scope and evidence limits: [CODEBASE_ANALYSIS.md](CODEBASE_ANALYSIS.md). This is a source audit, not a penetration test or a production security certification. No credential validity was tested. No patient data or log contents were read. Severities describe plausible impact if this snapshot is deployed and reachable; exploitability depends on external controls that have not been verified.

## Secrets response and privacy boundaries

Credential locations above intentionally exclude values and fingerprints. Existing source remains unchanged under this assignment's read-only constraint; it therefore still contains the exposed values. No push or commit was made. Keep this snapshot restricted. Owner should identify every credential issuer and affected release before coordinated revocation, including both Redis databases, both sending configurations, webhook verification values, browser copies and backups. Do not paste replacement secrets into conversation; store them in a deployment secret manager or protected local environment file outside version control when implementation is authorized.

Rotation is an owner action requiring a continuity window: provision replacement, deploy server-only configuration through the approved process, verify using a test sender, revoke old values and check for remaining privileged browser access. Do not retain compromised browser credentials as a rollback mechanism. No compromise of an account or exfiltration is proven by the source exposure alone.

Do not import historical logs into Supabase by default. Approve purpose, access, retention, backups and deletion separately for health data, numbers, addresses, payment images and audit metadata. No claim of regulatory compliance is made; jurisdiction/data-controller decisions require the appropriate owner.

## Primary technical references

- [Meta webhook payload validation](https://developers.facebook.com/docs/graph-api/webhooks/getting-started/#validate-payloads): signature verification requires the app secret and raw request payload.
- [Firebase ID token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens) and [session revocation](https://firebase.google.com/docs/auth/admin/manage-sessions): server validation and revocation are distinct from client state.
- [Supabase Firebase integration](https://supabase.com/docs/guides/auth/third-party/firebase-auth) and [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security): third-party identity still requires authorization policies; privileged service access must remain server-only.
