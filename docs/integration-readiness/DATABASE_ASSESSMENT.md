## Compatibility with the local draft

The private migration is `supabase/migrations/202611200001_rudo_private.sql`, checksum recorded in [local test evidence](../LOCAL_TEST_RESULTS.json). Its ten tables, three functions and policies were tested locally; the checksum is unchanged. Its `CREATE SCHEMA rudo` fails if unexpectedly present; local-ledger reruns are distinct from re-executing raw SQL.

| Contract difference | Why direct binding/replacement fails |
|---|---|
| Public messages use bigint id + phone; local messages use UUID conversation FK and provider/account metadata | No lossless automatic public-to-private relationship or provider ID mapping exists |
| Public source has no account/facility dimension | A global facility default, QR source or country code is not an authorization assignment; unmapped records must remain inaccessible |
| Local history permits custom roles, public messages CHECK only user/bot | Staff/system metadata cannot be inserted as a new public role without an approved contract change |
| Public orders/referrals use GENERATED ALWAYS identity | Explicit source IDs need a reviewed restore/import method in staging; an ordinary INSERT preserving IDs is not automatically compatible |
| Public orders store fields directly; local orders wrap source payload and add version/status control | Current local order methods cannot simply point to public.orders; bot reads/writes and optimistic concurrency require an adapter/ownership decision |
| users.state JSONB and separate user_state | No verified field/identity mapping; state reset or replacement could interrupt language, shop or handoff workflows |
| Public messages omit provider IDs and some real interactions | Legacy delivery state is unknown; do not synthesize wamid or delivery success from body/time/role |
| Existing local importer consumes Redis-shaped string exports | It is not a public-Supabase-to-dashboard adapter or a verified cross-store merger (`rudo/importer.py:30–110`) |
| Local read methods append private audit events and every remote connection needs the broad remote flag | Current implementation is not a remote read-only observer merely by changing its DSN |

Changes cannot be observed reliably from an ID watermark alone: candidate db.py patches message_en and exposes history-delete helpers, while public.messages has no updated_at and no trigger was found. users.updated_at has a default but no update trigger; its maintenance depends on the writer. Any later copied change feed must handle edits/deletes and verify every writer's contract. The proposed initial adapter reads the authoritative source instead of introducing such a copied feed.

## Options comparison

| Criterion | A — Existing public tables | B — Full isolated rudo business store | C — Controlled adapter + private control metadata |
|---|---|---|---|
| Security | Can be secure with dedicated roles, scope mapping and reviewed policies; broad grants and missing scope currently block staff access | Local roles/scopes already modeled; second sensitive-data copy and worker boundary increase obligations | Narrow read projections and private memberships; interface/policy implementation must be audited |
| Consistency | One existing store if authoritative writer is verified | Two independent histories until migration/ownership cutover is solved; highest split-brain risk | One authoritative clinical/business store; metadata overlays, no default history replication |
| Operational complexity | Fewer stores; staff and bot contracts become tightly coupled | Import, catch-up, duplicate handling, reverse replay and expiry parity required | Adapter/version contract and authorization joins required; substantially smaller initial release |
| Migration risk | Public extensions/policies might affect unknown consumers | Full data/identity/state migration; bot persistence adapter required | Stage with synthetic source-shaped data; production initially additive access/control changes only after approval |
| Bot compatibility | Best chance of retaining exact existing table contract; must inventory writers | Candidate bot must change or be bridged to keep working | Bot keeps existing persistence/inference paths for first observer release |
| Rollback difficulty | Depends on any public data/schema changes | Hard after target-only writes; replay and state reconciliation needed | Read-only feature can be disabled without replaying patient history; revoke observer access if needed |
| Maintainability | Good if shared schema contract/versioning is owned | Good only after a deliberate convergence/cutover project | Good if thin and single-source; poor if allowed to grow into permanent bidirectional synchronization |

**Recommendation: Option C, initially read-only.** Existing public tables are the leading candidate source, conditional on authoritative-writer verification. Keep clinical/business history at its verified source and use a private control plane for approved staff identity, facility/source mappings, access audit and any necessary display metadata. Do not apply the entire current private business-schema draft unchanged as the integration decision.

This recommendation can be revised if the owner demonstrates that another store is authoritative or authorizes full bot/data consolidation. It does not assume the candidate repository is deployed or that all public data should be migrated.

## Smallest safe access design to approve for staging

1. Recreate the inspected public table shapes using **synthetic fixtures** in an isolated staging/local environment. Add only reviewed private membership/source-scope metadata there. No production content copy is needed to prove the adapter.
2. Give an independent observer role no INSERT/UPDATE/DELETE/TRUNCATE/CREATE or membership-management capability. Under current public RLS, SELECT grants alone are insufficient: staging needs explicit observer-only SELECT policies using protected scope helpers, or an independently reviewed narrow function interface. Do not disable RLS, grant a browser service key, or expose a generic SECURITY DEFINER SQL executor.
3. Derive issuer/subject only from verified Firebase tokens and use dedicated backend connections. Application-set session context is a trusted backend assertion, not a JWT independently verified by PostgreSQL. Never give browser/API-wide roles the backend database credential or membership in its runtime roles.
4. Read projected columns with keyset pagination. List conversation summaries first; fetch thread history on demand. The current N+1 full-history list (`rudo/db.py:61–82`, `js/rudo-api.js:30–37`) needs adaptation and load testing before a live observer is safe.
5. Keep public data transactions read-only; route access audit to a separate append-only private channel. Disable staff mutation APIs at the server and with database privileges. Hiding send buttons or enabling RUDO_ENABLE_REMOTE_WRITES is not a read-only boundary.
6. Validate unknown facility/account mappings deny access. Approve account/phone/thread relationships and phone reuse explicitly; do not infer facility from referrals or assume all records belong to one configured account.
7. Use the bot's synthetic staging writes to demonstrate dashboard visibility without altering inference, send count, state updates or AI context. No two-way synchronization or duplicate webhook consumer is needed for this slice.

Future public policies/functions, private control tables and runtime grants are **proposals** requiring architecture and staging authorization; no executable integration migration was added in this audit. Data import/backfill, when later needed, requires consistent backup, approved lineage, identifier/sequence handling, absolute expiry and reconciliation beyond row counts.
